# Мультиплеер — план

Решения пользователя (2026-11-20): комнаты по ссылке/коду, гость с ником (без паролей), сейчас 1×1, но
архитектура под 2–4 игроков. Хостинг ещё не выбран (возможно, вне РФ) — сервер переносимый: Node + Postgres в Docker.

## Архитектура

```
apps/mobile          клиент (Expo): лобби, комната ожидания, онлайн-матч; матч с ботом остаётся офлайн
apps/server          Node 22 + TypeScript: Fastify (HTTP) + Socket.IO (realtime), Postgres
packages/game-core   правила — одни и те же на клиенте (бот-матч) и на сервере (онлайн)
packages/protocol    типы сообщений клиент ↔ сервер и HTTP-ответов (общие для обоих)
docker-compose.yml   Postgres 16 на порту 5433 (не трогаем локальный 5432)
```

**Сервер авторитетный.** Только сервер держит `GameContext` с ответами и вызывает `dispatch`. Клиент шлёт намерения
(`answer`, `boost`, `pick`, `attack`, `wager`, `continue`), сервер валидирует через `dispatch` (недопустимое
действие возвращает тот же state) и рассылает новый `MatchState` всем в комнате. В `MatchState` вопросы уже лежат
как `PublicQuestion` без ответа — состояние можно отдавать клиентам целиком.

**Время.** Сервер ставит `answersAt` (пауза на чтение) и дедлайн; `elapsedMs` считает сам по времени получения
ответа. По дедлайну + 1,5 с grace сервер сам отправляет `ANSWER null` за молчащих. Разбор (`reveal`) закрывается,
когда все нажали «Дальше», либо автоматически через 8 с.

**Отключения.** Игрок может переподключиться (тот же гостевой токен) и получит текущее состояние. Если игрок
отсутствует, его ходы делает таймер: вопрос — без ответа, выбор/атака — случайный допустимый вариант через 20 с.

## Этапы

**A. game-core на N игроков** (2–4): `PlayerId` → места `"p1".."p4"`, `state.players`, столицы и щиты на каждого,
ранжирование раздела по местам (1-е — 2 планеты, 2-е — 1, остальные — 0), ход атаки по кругу, финал «Ва-банк» на всех,
победа — последний со столицей или больше всех очков. Карта генерируется/выбирается по числу игроков (2: текущая
Солнечная система; 3–4: новые раскладки). Матч с ботом работает на тех же типах (`p1` = человек, `p2` = бот).
Мобильный клиент переводится на новые типы без изменения внешнего вида.

**B1. Сервер** (`apps/server`, `packages/protocol`, `docker-compose.yml`): гостевая регистрация
(`POST /guest {nickname}` → токен), комнаты (`create` → код из 4 символов, `join`, готовность, старт хостом),
матч-цикл, таблицы `players`, `rooms`, `matches`, `match_players`, `match_events`; интеграционные тесты на
двух socket-клиентах (полный матч).

**B2. Клиент**: экран ника, «Играть с друзьями» → создать комнату / ввести код, ссылка-приглашение
(`/room/ABCD`), комната ожидания с игроками и готовностью, онлайн-матч на тех же компонентах, индикатор связи и
переподключение.

**C. Проверка**: две вкладки браузера играют матч от начала до конца; обрывы связи; три игрока (без UI-полировки).

## Локальный запуск (после B)

```bash
docker compose up -d db        # Postgres на 5433
npm run server                 # API + realtime на 3001
npm run web                    # клиент на 8081, EXPO_PUBLIC_SERVER_URL=http://localhost:3001
```

## Онлайн-режим локально

```bash
npm run db:up                  # docker compose up -d --wait db — Postgres 16 на localhost:5433 (5432 не трогаем)
npm run server                 # apps/server: tsx watch, HTTP + Socket.IO на :3001, миграции применяются при старте
npm run server:test            # интеграционные тесты (нужна поднятая db; каждый прогон — своя временная схема)
npm run db:down                # остановить Postgres (данные остаются в volume conquistador-db)
```

Проверка: `curl localhost:3001/health` → `{"ok":true}`.

Переменные окружения сервера (все необязательные):

| Переменная | По умолчанию | Что это |
| --- | --- | --- |
| `DATABASE_URL` | `postgres://conquistador:conquistador@localhost:5433/conquistador` | Postgres |
| `DB_SCHEMA` | — (public) | схема для таблиц (тесты создают свою `t_…`) |
| `PORT` / `HOST` | `3001` / `0.0.0.0` | где слушать |
| `CORS_ORIGINS` | вне production — любой origin; в production — `http://localhost:8081` | список через запятую, `*` — любой |
| `QUESTIONS_DIR` | `content/questions` | банк вопросов: все `*.json` (как у клиента) |
| `ANSWER_GRACE_MS`, `REVEAL_AUTO_CONTINUE_MS`, `TURN_TIMEOUT_MS` | 1500 / 8000 / 20000 | тайминги из `TIMING` протокола |
| `OFFLINE_MOVE_DELAY_MS` | 2000 | через сколько сервер ходит за отключившегося |
| `ABANDON_AFTER_MS` | 120000 | все игроки офлайн: матч на паузе, после этого срока — прерван |
| `LOG` | `1` | `0` — без логов Fastify |

Устройство (`apps/server/src`): `config.ts` (env, тайминги, `readingMs` — та же формула, что в клиенте),
`db.ts`/`migrate.ts` (postgres.js, SQL-миграции `apps/server/migrations/*.sql`, учёт в `schema_migrations`),
`auth.ts` (гости, в БД только sha256 токена), `rooms.ts` (комнаты, присутствие сокетов, запуск матчей),
`matchRunner.ts` (авторитетный цикл матча, один таймер на матч, инъецируемые часы), `matchRepo.ts` (запись матча),
`http.ts` (Fastify), `socket.ts` (Socket.IO, ack на каждое событие), `app.ts`/`main.ts` (сборка и запуск).

Таблицы: `players`, `rooms`, `room_members`, `matches` (с `rng_seed` и `final_state`), `match_players`
(места, очки, места в итоге), `match_events` (каждое принятое действие по порядку, `source`: player / timeout / auto).
Сид + события воспроизводят матч точно (`createMatch` с тем же сидом + `dispatch` по событиям) — это проверяет тест.

Правила сервера сверх плана:
- Пока вопрос открыт, клиент не видит чужих ответов (только факт ответа), чужих подсказок и `choiceOrder`
  (в контенте верный вариант почти всегда первый — порядок выдал бы ответ); чужие ставки в «Ва-банке» — нули.
- Ответ до `answersAt` (пауза на чтение) отклоняется; `elapsedMs` считает сервер по времени получения.
- За отключившегося: вопрос — «без ответа», как только все онлайн-игроки ответили (через `OFFLINE_MOVE_DELAY_MS`),
  иначе по дедлайну; выбор / атака / ставка — ходом бота уровня normal через `OFFLINE_MOVE_DELAY_MS`
  (за игрока онлайн, который бездействует, — через `TURN_TIMEOUT_MS`).
- Все игроки офлайн — матч на паузе (часы сдвигаются на длину паузы); через `ABANDON_AFTER_MS` матч прерывается,
  комната возвращается в лобби.
- Переподключение: тот же токен → `room:join` → свежий `match:snapshot` (или `match:sync`).

Ограничения: живые матчи только в памяти одного процесса. Комнаты и история переживают рестарт, а идущие матчи —
нет: при старте сервер помечает их `aborted`, а комнаты возвращает в лобби (участники остаются, готовность сброшена).
Горизонтально масштабировать нельзя без общего хранилища состояния. Клиентский бандл содержит весь банк вопросов
(для офлайн-бота), так что знающий клиент может найти ответ по тексту вопроса — это не решается на сервере.
